# 方案文档生成与收敛

方案固定写入 `.specs/<KEY>/solution.md`。有 Issue 时优先用其 key；没有时用 `LOCAL-YYYYMMDD-<SHORT-SLUG>`。同一任务只保留一个当前方案，不创建“最终版”或机器状态文件。

确认后的 `solution.md` 是方案任务的业务与技术中心；Issue、飞书等是初始来源，Acceptance、人工验收和实施报告是从属附件。方案出现会改变范围、行为、权限、数据、兼容或不可逆结果的修改时，更新正文并重新确认受影响内容。本阶段不写业务代码、不执行 DDL 或迁移、不修改外部 Issue。

读取 `AGENTS.md`、当前请求、已确认补充、存在的 Issue 与关联材料、相关入口与消费方、模型与迁移链、HTTP/MQ 契约、配置、测试，以及 [solution.template.md](solution.template.md)。写真实路径前必须亲自核实代码。

## 章节选择

始终保留需求描述、现状与问题、业务流程、文件结构与实现方案、验证与验收。

- 涉及生命周期、持久化状态、状态决定操作、并发、重试或恢复时，必须保留状态机；
- 只要读写持久数据就保留数据模型；
- 改变 HTTP、MQ 消息、共享 schema、配置键、文件格式或 Java 消费契约时保留接口与消息契约；
- 整体架构、模块分解、外部服务与安全、实施顺序、已确认决策、风险与依赖按真实命中保留。

未命中章节整章删除，不写空表或“不涉及”。

## 内容要求

- 第一部分只讲业务；每个可观察结果编号 `R1`、`R2`，关键规则编号 `BR1`、`BR2`。
- 主要流程保留一张匹配内容的 Mermaid 图；状态、交互或实体关系确实复杂时再增加图。
- 数据变化必须核实 ORM、Alembic head 与目标环境 revision；目标环境无法核实时写“尚未核实”。`migrations/db.sql` 是冻结 baseline，不得修改。
- HTTP/MQ 契约写清输入、输出、错误、权限、消费方、兼容、发布顺序和失败结果；MQ 变化覆盖 Java 消费方与文档同步面。
- 代码实施计划按依赖编号，每行只有一个真实文件、一个动作、明确职责、依赖或消费方、完成判据，并引用承接的 `R/BR`。
- 每个 `R` 和决定行为的 `BR` 都映射到真实测试文件、具体命令或人工步骤；计划不得写成已通过证据。

能从代码或材料核实的事实自行调查；不改变外部结果的普通细节沿用仓库惯例；改变范围、规则、数据、权限、状态、兼容、失败表现、架构、外部依赖、运行成本或性能上限时必须提问。一次只问一个上游问题，复杂单题可调用 `decision-grilling`。

用户未选择后续路径时，在方案确认时同时确认：`直接施工` 使用方案中的验证映射；`契约验收` 再由 `acceptance-generator` 展开需要独立确认的 Gherkin。方案确认后返回 `backend-delivery` 拆分工作包。
