# 后端七维判断与交付

当前对话的主 Agent 始终拥有用户沟通、授权、判断、方案、工作包拆分、工作区协调、整合和复核。不要仅因任务复杂、需要方案或风险严格而创建同级规划 Agent。

```text
backend-delivery
  ├── 需调查或澄清 → 最小只读调查 / 一个关键问题
  ├── 模块目标未成形 → module-planning
  ├── 直接实现 → implementation-execution
  └── 方案先行 → solution-generator
                    ├── 直接施工 → implementation-execution
                    └── 契约验收 → acceptance-generator → implementation-execution
  → test-authoring（按需）→ run-all-tests → manual-acceptance（按需）
  → code-review-and-quality → branch-pr-workflow（另有 Git 授权时）
```

来源可以是当前请求、Issue、飞书文档或用户指定材料。存在 Issue 时完整读取；没有 Issue 不阻止开发。

## 七维判断

自动或开启工作流时分别判断：准备程度；影响面与牵连；规则与状态关系；实现确定程度；验证难度；风险与可回退性；持续性与协作。

复杂度只由影响面、规则关系、实现确定度和验证难度决定：四项都简单才是简单；任一项有明确复杂信号就是复杂；其余为中等。权限、安全、数据、公开契约、生产切换或不可逆操作属于严格风险，但风险严格和持久记录都不单独把任务升级为方案先行。

## 路径映射

1. 整个模块目标或商业前提未形成：`module-planning`；
2. 缺少会改变结果的事实或选择：调查或只问一个关键问题；
3. 复杂任务：方案先行；
4. 简单任务：直接实现；
5. 中等任务只有目标收敛、消费方找全、实现可逆、无需兼容窗口或迁移、验收可用短清单表达时直接实现，否则方案先行。

数据库 schema、存量数据迁移、MQ 公共消息、跨 Java 消费方兼容通常需要方案先行，因为它们经常命中迁移顺序、兼容和回退，而不是因为标签本身构成硬门槛。

用户明确指定的路径优先：指定直接实现时只识别阻塞事实和严格检查，不静默升级；指定方案先行时不降级；`工作流：关闭` 不创建 Spec，由主 Agent 给出最小实施边界后施工。

默认只向用户展示路径、一个主导原因和额外检查。准备不足、风险严格、需要持久记录或用户要求时，再展开七个维度、预计影响、未确认项和下一站。

## 工作包与完成

实施前写清每个工作包的目标、可观察结果、允许与禁止文件、文件所有权、依赖、严格检查和最小验证。能独立完成、文件不重叠且无前置依赖的工作包可以并行；共享契约、迁移链、同一核心文件或存在前后依赖时必须串行。不要为了形式拆分紧密耦合的工作。

实施 Agent 必须使用 `implementation-execution`，不得自行创建分支、提交、推送、PR 或修改外部系统。发现新业务、权限、数据、兼容或发布决定时回到 `solution-generator` 或本技能，不允许在代码里静默改写要求。

实现完成后按真实影响进入 `run-all-tests`、适用的 `manual-acceptance` 和 `code-review-and-quality`。只有用户另行授权 Git 交付时才进入 `branch-pr-workflow`。
